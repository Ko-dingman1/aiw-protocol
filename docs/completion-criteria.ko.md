# 완성도를 판단하는 기준

기능 개수만으로 완벽함을 보장할 수는 없습니다. 목표 사용자, 지원 환경, 실패 시 동작을 정하고 그 약속을 검증해야 합니다. 현재 목표는 **로컬에서 재현 가능한 지식 교환 프로토콜 연구·포트폴리오**입니다. 아래 8개 영역은 이 프로젝트를 위한 기준이며 보편적인 인증이나 완성도 점수가 아닙니다.

| 영역                  | 완료라고 말할 근거                            | 현재 범위                                                 |
| --------------------- | --------------------------------------------- | --------------------------------------------------------- |
| 1. 발견과 직접 조회   | Registry → Resolver → Node를 실제 HTTP로 통과 | 구현·통합 테스트                                          |
| 2. 데이터 계약        | 잘못된 값·단위·스키마를 거부                  | v0.3 도메인 규칙·테스트                                   |
| 3. 출처와 불일치      | 제공자별 상충 값을 유지하고 출처·근거 표시    | 데모·UI·테스트                                            |
| 4. 참조 재현          | 과거 입력 버전 조회와 보관 만료 오류          | v0.3 메모리 이력·테스트                                   |
| 5. 조회와 갱신        | 제한된 페이지, SSE, 잘못된 커서·끊김 처리     | 테스트; SSE 재전송 미지원                                 |
| 6. 실제 연동과 장애   | 실데이터 변환·캐시·시간 제한·오류 표기        | Open-Meteo; 실패는 주입 테스트                            |
| 7. 확인 가능한 화면   | 검색·필터·출처·버전 선택·원본 확인            | 한국어 대시보드 구현; v0.3 화면 검증은 도구 오류로 미완료 |
| 8. 재현 가능한 배포물 | 설치·문서·테스트·빌드·다중 OS CI              | 저장소·버전 태그; 공개 서비스 배포 아님                   |

이 범위가 검증되면 “출처와 버전 참조를 보존하는 지식 교환 프로토타입을 구현하고 실패 시나리오까지 테스트했다”고 말할 수 있습니다. “완벽한 AI 인터넷”이나 “실서비스 준비 완료”는 현재 범위를 넘습니다.

## 운영형 제품을 위한 6개 큰 과제

1. **인증과 권한:** OAuth/OIDC/mTLS 등 적절한 기존 체계로 등록·갱신 권한과 테넌트 분리를 검증합니다.
2. **영구 저장과 복구:** 재시작·장애 복구, 백업 복원 시험, 마이그레이션과 삭제 정책이 필요합니다.
3. **여러 노드의 신뢰:** 소유권 확인, 원격 주소 검증, SSRF 방어, 오래된 등록 만료가 필요합니다.
4. **운영 관측성:** 상태 점검, 오류·지연·용량 지표, 감사 기록, 알림, 배포·롤백 절차가 필요합니다.
5. **부하·장애·보안 시험:** 목표 사용자 수와 데이터량을 정하고 한계와 복구 동작을 검증합니다.
6. **외부 사용자 검증:** 다른 개발자가 문서만으로 노드·어댑터를 만들고 실제 사례에 적용해 봐야 합니다.

따라서 추가 기능의 개수가 아닌 위 8개 영역의 재현 가능성이 포트폴리오의 기준입니다. 운영형 제품은 별도의 6개 큰 과제를 추가 검증해야 하며, 각 과제에 여러 구현과 테스트가 포함됩니다. v1.0은 그때 정한 지원 범위와 품질 기준으로 판단합니다.
